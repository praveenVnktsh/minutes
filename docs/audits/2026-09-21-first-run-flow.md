# Minutes first-run flow investigation — 2026-09-21

## Summary

The first-run flow is four screens — Welcome, Setup Overview, Download Progress, Permissions (macOS only) — and it ends when two files exist on disk. Nothing in it ever opens the microphone for a level, loads the transcription engine it just downloaded, or turns a second of the user's speech into text. The ticket author's suspicion is borne out by the code and is **FR-01**: setup concludes at "model downloaded", and the first time the engine is asked to do real work on a default fresh install is in the deferred transcription queue, after the user's first real meeting has already ended.

Around that centre are three more classes of defect. The permission step certifies grants it has not observed — both rows can paint "Access Granted" on evidence that a denial also produces — and the one recovery button on that screen invokes a Tauri command without its required argument, so it cannot work. The download step begins roughly 3.41 GB of transfer on arrival, with no size shown beforehand, no time estimate anywhere in the stack, no label on the blocking button and no way to cancel or defer. And the summary-model downloader leaks its in-flight reservation on the one failure path that a disconnected machine takes, so the "Try Again" button it offers can never succeed again for the life of the process.

This investigation identifies **23 findings: 6 P1, 10 P2, and 7 P3**. P1 means a new user is blocked, loses data, or has reason to quit. P2 is friction or a missing recovery path. P3 is copy and verified cleanup debt.

Two concerns that a first-run review would reasonably raise do **not** hold, and are recorded here rather than as findings. Both downloaders resume by HTTP `Range` against the existing partial file (`frontend/src-tauri/src/summary/summary_engine/model_manager.rs:462-529`; `frontend/src-tauri/src/parakeet_engine/parakeet_engine.rs:700-701, 912-991`), so a drop at 95% does not restart from zero. And both HTTP clients carry a 30-second connect timeout and a 30-second per-chunk stall timeout (`model_manager.rs:477, 588`; `parakeet_engine.rs:869, 1006`), so a dead network fails within a bounded window rather than hanging indefinitely.

**Evidence boundary:** this is a code trace and nothing more. It ran on Linux, with no macOS host, no Mac hardware, no display, and no installed canary build. The application was never launched. No screen was seen, no button was clicked, no screen recording was captured, no TCC permission was granted, denied or revoked, no download was run, and no duration was measured — every number below is either read out of a source constant or derived from one with the arithmetic shown, never observed. No build, test, `cargo check` or `pnpm` command was run. Where a claim depends on what macOS actually does, it is attributed to the repository's own comments and labelled as such. Every runtime-dependent question the probes raised is in the closing "What the Mac run still has to answer" section, not in the findings list. Line references describe the working tree at branch `foreman/minutes/PRA-497`, clean at `4c93391`. Paths in the findings are relative to `frontend/src/` unless prefixed otherwise.

**The step order in the ticket text is wrong.** `components/onboarding/OnboardingFlow.tsx:42-45` renders `1 → WelcomeStep`, `2 → SetupOverviewStep`, `3 → DownloadProgressStep`, `4 → PermissionsStep && isMac`, each step hard-codes the same number into its container (`steps/WelcomeStep.tsx:29`, `steps/SetupOverviewStep.tsx:50`, `steps/DownloadProgressStep.tsx:495`, `steps/PermissionsStep.tsx:118`), and `goNext` clamps at 4 (`contexts/OnboardingContext.tsx:595-601`). Permissions is **last**, after the downloads, and only on macOS. All five probes agreed on this against the ticket; the code confirms them.

## Findings and fix contracts

### FR-01 · P1 — Setup ends at "the file is on disk"; nothing ever captures, loads, or transcribes anything

**Evidence:** two searches across `components/onboarding/**` and `contexts/OnboardingContext.tsx` establish the negative. No call site invokes `start_audio_level_monitoring`, `list_audio_devices`, `parakeet_transcribe_audio`, or any recording command; the only matches for recording/transcription vocabulary are prose in UI copy (`steps/WelcomeStep.tsx:28`, `steps/PermissionsStep.tsx:117, 162`, `steps/DownloadProgressStep.tsx:374`) and the state key `screenRecording` (`contexts/OnboardingContext.tsx:105`). There is no mic test, no level meter, no sample transcript, no playback.

Nor is the engine ever loaded. Onboarding touches Parakeet three ways, none of which loads weights: `parakeet_init` only constructs the engine object and returns (`frontend/src-tauri/src/parakeet_engine/commands.rs:40-52`), and it already ran at app startup; `parakeet_has_available_models` resolves to a filesystem check that compares four file sizes against `ArtifactSpec.exact_bytes` (`parakeet_engine.rs:413-429`); and the command that actually calls `load_model` (`parakeet_engine.rs:432`) is `parakeet_load_model`, registered at `frontend/src-tauri/src/lib.rs:848`, whose only frontend wrapper is `ParakeetAPI.loadModel` (`lib/parakeet.ts:177-179`) — which has no caller anywhere in the repository.

The first real load therefore happens through `validate_transcription_model_ready` (`frontend/src-tauri/src/audio/transcription/engine.rs:114-137`), and recording start calls that **only when live transcription is on** (`frontend/src-tauri/src/audio/recording_commands.rs:589-611`; the `else` branch logs "Deferred transcription mode: skipping startup model validation"). Live transcription is off on a clean install: `isLiveTranscriptionEnabled` returns `storedValue === 'true'` when the toggle feature is available (`lib/liveTranscription.ts:8-13`), the toggle defaults to available (`types/betaFeatures.ts:32-35`), and a fresh profile has no `liveTranscriptEnabled` key (`contexts/RecordingControllerContext.tsx:445-448`). The frontend pre-flight is inside the same `if` and in any case only calls the byte-count check (`contexts/RecordingControllerContext.tsx:460-470`).

**Impact:** a new user completes setup having watched two progress bars and dismissed a permission sheet. Nothing demonstrated that the microphone produces signal, that the selected input is the one they expect, that system audio is routed, or that the 639.6 MiB engine can turn sound into text. Their confidence at the end of onboarding is borrowed entirely from a percentage reaching 100. On the default fresh Mac install the first time the engine is asked to do anything real is in the deferred queue, *after* a real meeting has been recorded — so a missing ONNX runtime, a model corrupt in a way four exact file sizes do not catch, or an allocation failure is discovered once the meeting is already spent.

**Fix contract:** setup proves the thing it exists to establish. Load the model once inside onboarding, immediately after the download reports complete, and treat a load failure as a first-class onboarding outcome with retry and re-download rather than a console warning. Add a terminal "check your setup" step that reuses the already-loaded engine: capture a few seconds of microphone and system audio, show a live level meter per channel, transcribe the captured buffer locally, and show the user their own words. Report per channel, never as one composite — "mic fine, system audio silent" is the expected clean-Mac outcome and must not collapse into a single red state. Each distinct failure routes to its own remediation: permission sheet, device picker, system-audio routing guidance, model retry. The step is skippable without blocking completion, and its outcome is recorded so the app can offer it again from settings. It replaces nothing: the download step still gates on the model existing; this step gates on the model *working*. Every command it needs is already registered — `parakeet_load_model`, `parakeet_is_model_loaded`, `parakeet_validate_model_ready_with_config`, `parakeet_transcribe_audio`, `start_audio_level_monitoring`, `list_audio_devices` — so this is orchestration, not new native capability. Separately, the deferred-transcription start path should validate that the engine loads *before* capture begins, using the validation call it currently skips, so a broken engine is reported while the meeting can still be re-run.

### FR-02 · P1 — System Audio reports "Access Granted" on tap construction alone, and the UI claims a silence check that does not exist

**Evidence:** `steps/PermissionsStep.tsx:75-76` comments the call as "Backend creates Core Audio tap, captures audio, and verifies it's not silence / Returns true if permission granted and audio verified, false if denied (silence)", and on success logs "Audio Capture permission verified - audio is not silence" (`:82`). The backend does none of that. `trigger_system_audio_permission` (`frontend/src-tauri/src/audio/permissions.rs:95-125`) constructs `CoreAudioCapture::new()`, sleeps 500 ms and returns `Ok(true)`; its own comment at `:100` says "We only create the tap, don't start streaming", and at `:108-109` it states the opposite of the UI's claim — "even with permission denied, tap creation may succeed but audio will be silence. For onboarding, we just check tap creation." `Ok(false)` is returned only when `new()` errors (`:112-123`). The UI maps `true` straight to `authorized` (`:80-82`), which paints "Access Granted" (`components/onboarding/shared/PermissionRow.tsx:42-47`), removes the row's only button (`:61`), and enables Finish Setup (`steps/PermissionsStep.tsx:110-112, 149`).

**Impact:** on the permission macOS 14.4+ actually requires for system audio, a user is told the channel is ready when the TCC grant may not exist. The failure surfaces much later as a meeting recorded with the far end silent — the exact outcome onboarding exists to prevent — and the user has no reason to suspect the permission, because setup said it was granted. The comment drift compounds it: the next maintainer reading `PermissionsStep.tsx` will believe a verification exists.

**Fix contract:** one backend verifier owns "can we actually capture system audio" and returns a tri-state — `authorized`, `denied`, `undetermined` — never a bool. It reaches `authorized` only on observed tap output within a bounded wait, not on object construction, and reports anything else as not-yet-granted with the reason. The three outcomes (denied, granted-but-silent, granted-and-audible) need three different next actions, and only the third may render green. The Rust doc comment, the TypeScript comment and the log strings state the same contract, or the verification language is deleted and the row honestly reads "permission requested, outcome unknown until first recording".

### FR-03 · P1 — The microphone grant is recorded after a fixed 500 ms sleep, using the check the repo itself documents as blind to a denial

**Evidence:** Enable invokes `trigger_microphone_permission` (`steps/PermissionsStep.tsx:43`) → `frontend/src-tauri/src/lib.rs:410-413` → `audio/devices/discovery.rs:46-98`, which builds an input stream, calls `play()`, sleeps a fixed 500 ms and returns `Ok(true)` with the comment "If we got here, permission was granted" (`:88-97`). No audio callback is awaited. Sixty lines below in the same file sits the stronger check, `verify_microphone_access`, carrying the contradicting doc comment: "A macOS TCC denial can still let an input stream be *created*, but the audio callback then never fires" (`discovery.rs:100-111`). It therefore waits up to 5 s for the first callback before erroring (`:147-161`) — and it is wired into the record-start path (`audio/recording_commands.rs:549`), not into onboarding. `steps/PermissionsStep.tsx:46-51` maps `true → 'authorized'`.

**Impact:** by the repository's own account of macOS behaviour, a denied microphone still permits stream creation, so the weak check returns `true` and the row goes green. The macOS permission sheet is modal and a human answer takes longer than 500 ms, so the row can also flip to "Access Granted" while the dialog is still on screen and stay green if the user then clicks Don't Allow. The `denied` branch (`steps/PermissionsStep.tsx:30-38`) and the red row styling (`PermissionRow.tsx:23, 47-51`) are close to unreachable on first click. Setup certifies exactly what recording will later reject, using a weaker test than the one the repo already trusts at record time.

**Fix contract:** onboarding and record-start share one microphone verifier — the callback-observing one — so setup cannot certify what recording rejects. It returns a three-state result: `authorized` means audio was observed, `denied` means the stream ran but stayed dead, and a distinct `unavailable` covers "no input device". The command resolves only once the permission state is actually determined; the row shows a pending state until then rather than a result, and a timeout is reported as undetermined with a retry, never as granted. No code path may infer `authorized` from stream construction.

### FR-04 · P1 — Both "Open Settings" buttons call the command without its required argument, so the only recovery route is a raw `alert()`

**Evidence:** both denied-state handlers call `await invoke('open_system_settings')` with no argument object (`steps/PermissionsStep.tsx:33, 65`). The command's signature requires one: `pub async fn open_system_settings(preference_pane: String)` (`frontend/src-tauri/src/utils.rs:10-12`, registered under the same macOS cfg at `lib.rs:1028-1029`), and the parameter is what builds the pane URL at `utils.rs:16`. A Tauri command whose required argument is absent fails argument deserialisation and rejects, so the `catch` runs and the user gets a browser `alert()` reciting a settings path (`:35, 67`). The only other caller in the repository passes it correctly: `components/PermissionWarning.tsx:37` sends `{ preferencePane: 'Privacy_Microphone' }` and `:47` sends `'Privacy_ScreenCapture'`. The alert text for system audio names "Privacy & Security → Audio Capture", which the repo's own code says has no direct URL (`frontend/src-tauri/src/audio/permissions.rs:38-41`).

**Impact:** the single recovery affordance on the permissions step — the button that appears once a row is `denied`, in the one state where macOS will not re-prompt — never opens System Settings. The user gets an unstyled modal alert and must navigate Privacy & Security by hand. Combined with FR-02 and FR-03, the rare case where the app correctly detects a denial is the case that leads to a dead end.

**Fix contract:** pass the pane at both call sites exactly as the non-onboarding caller already does, behind the same platform test that decides whether the step renders, since the command does not exist off macOS. Demote `alert()` from the normal path to a genuine fallback, routed through the app's standard feedback surface with the current pane name. Keep the row in its denied state with a visible re-check action so a user who grants the permission externally can return and confirm it without restarting the flow. A test asserting the invoke payload shape for every `open_system_settings` call site would have caught the divergence between the two callers.

### FR-05 · P1 — 3.41 GB starts downloading unannounced, and the blocking wait has no estimate, no button label and no exit

**Evidence:** Welcome promises "Takes less than 3 minutes" unconditionally (`steps/WelcomeStep.tsx:61`). Setup Overview names the two downloads but shows no size, no duration and no network warning (`steps/SetupOverviewStep.tsx:29-40, 48-49`). Sizes first appear on screen 3 — where the transfers have *already been started* by mount effects before any click (`steps/DownloadProgressStep.tsx:169-195`) — and the only control there is a disabled Continue.

No time-remaining field exists end to end. The Rust progress struct carries `downloaded_bytes, total_bytes, downloaded_mb, total_mb, speed_mbps, percent` and no time field (`frontend/src-tauri/src/parakeet_engine/parakeet_engine.rs:39-52`; `summary/summary_engine/model_manager.rs:33-52`); the emitted payloads carry exactly those (`summary/summary_engine/commands.rs:152-164`); and the bar prints only bytes, a ~500 ms-window instantaneous speed and an integer percent (`steps/DownloadProgressStep.tsx:450-464`, speed computed at `model_manager.rs:666-676`). While `parakeetDownloaded` is false the primary button renders a bare spinner with **no text at all** (`:547-551`). There is no cancel, pause or defer control on either card, although `parakeet_cancel_download` and `builtin_ai_cancel_download` are both registered (`lib.rs:857, 965`). The reassurance "You can continue while this finishes" is gated on `parakeetDownloaded` and so appears only once the wait is already over (`:519-537`). The totals are those derived above: 670,619,706 bytes gating, plus 2614 MiB continuing, 3.41 GB in all.

**Impact:** the flow's longest unavoidable wait presents a full-screen overlay (`OnboardingContainer.tsx:46` is `fixed inset-0 … z-50`, and `app/layout.tsx:271-277` renders onboarding *instead of* the application), a percentage, and an unlabelled spinning button — with no answer to "how long" and no way out short of quitting. The cost is never disclosed before it is incurred: a user on a metered or slow connection is given no information on which to make a decision, and no decision to make. Holding the on-screen promise requires ~30 Mbit/s sustained for the gating download alone.

**Fix contract:** state the cost before incurring it. Setup Overview names both artifacts with byte sizes drawn from the same catalogue the downloader uses, says which one blocks the flow and which continues in the background, and the transfer begins on an explicit action on that screen rather than on the arrival of the next one. Carry remaining time as a first-class field from the downloader, where total bytes and a smoothed rate already exist, and render it beside the percentage with an explicit indeterminate state while the rate is unstable. The blocking button keeps a label naming what it waits for. The screen offers at least one honest exit — cancel with a stated consequence, or defer into a documented degraded state — wired to the cancel commands the backend already exposes. The three-minute claim is removed or replaced by something the app can honour.

### FR-06 · P1 — A failed summary download can never be retried again in the same app session

**Evidence:** `download_model_detailed` rejects a second request for a model already downloading (`summary/summary_engine/model_manager.rs:358-365`) and inserts the model name into `active_downloads` at `:371-375`, *before* any network I/O. Every later early-return path removes it again: non-2xx status at `:510-513`, cancellation at `:571-572`, per-chunk timeout at `:597-598`, stream error at `:622-623`, GGUF validation failure at `:748-749`. The connection attempt itself does not:

```rust
let response = request
    .send()
    .await
    .map_err(|e| anyhow!("Failed to start download: {}", e))?;   // model_manager.rs:492-495
```

This is the path a DNS or connect failure takes — "no network at all" — and the `?` returns with the reservation still held. The same leak exists at `Client::builder()` (`:479`), `create_dir_all` (`:459`), the file open at `:524`/`:528`, and the writer flush at `:714`. There is no guard or wrapper around the function, so nothing else clears the entry, and the `ModelManager` is process-scoped (`summary/summary_engine/commands.rs:46-58`). Thereafter every call — including the user's own Try Again, which invokes `builtin_ai_download_model` directly (`steps/DownloadProgressStep.tsx:128-134`) — hits the `active.contains` check at `model_manager.rs:360-364` and returns `Err("Download already in progress")` without attempting a connection, regardless of whether the network has returned.

The Parakeet downloader is the counter-example that shows this is not architectural: `download_model_detailed_from_source` always calls `finish_download` with the `Result`, `Ok` or `Err` (`parakeet_engine.rs:812-847`), and `finish_download` unconditionally removes the reservation and sets `ModelStatus::Missing` on failure (`:1133-1193`). The two engines render an identical "Try Again" button (`steps/DownloadProgressStep.tsx:474-485`).

**Impact:** a user who launches before connecting to Wi-Fi sees the Summary Engine card go to "Failed", reconnects, clicks Try Again, and gets `Download retry failed` forever — with a toast that says "Please check your connection and try again" (`steps/DownloadProgressStep.tsx:143-145`), which is actively wrong once the cause is an unreleased reservation. Because Continue is not gated on the summary model (`:544`), they finish onboarding and carry a permanently un-retryable summary engine into the app; only a full application restart clears it, and nothing tells them so. The app's own automatic retries hide the state further: `requestSummaryModelDownload` swallows any rejection whose text contains "Download already in progress" (`contexts/OnboardingContext.tsx:139-148`), and both callers — `startBackgroundDownloads` (`:546-547`) and `completeOnboarding` (`:493-495`) — cannot tell a legitimate in-flight download from a wedged one, so `summaryModelDownloaded` simply never becomes true with no visible reason. A reviewer who tests only the Transcription card would conclude retry works.

**Fix contract:** the reservation is released on every exit from the download, including the first network call and the client construction above it, by an RAII guard or by the always-called-finaliser discipline the Parakeet engine already demonstrates — not by adding one more `remove` to one more branch. "Already running" stops being an error for the caller: the command returns the existing download's handle, or at minimum is excluded from the error emission the way cancellation already is. And the string-matched "Download already in progress" filter is replaced by a dedicated error variant so the frontend can distinguish "in flight, ignore" from "stuck, surface it".

### FR-07 · P2 — Permission state is never read from the system, never re-read, and never persisted

**Evidence:** the context initialises all three permission fields to `'not_determined'` (`contexts/OnboardingContext.tsx:102-106`), and no code anywhere hydrates them from the OS. `PermissionsStep.checkPermissions` runs on mount but only `console.log`s the current React values, and its own comment says "Don't auto-set permissions based on device availability" (`steps/PermissionsStep.tsx:15-21`). The only writers are the two click handlers. No focus or visibility listener exists in `frontend/src` — a repo-wide search for `visibilitychange`, `document.hasFocus`, `tauri://focus` and `onFocusChanged` returns only an unrelated custom `focus-sidebar-search` event. Once a row is `authorized`, `PermissionRow.tsx:61` stops rendering its button entirely, so there is not even a manual re-check.

Nothing is written down either. The persisted payload contains only version, completion, step and model status (`contexts/OnboardingContext.tsx:453-464`), and `OnboardingStatus` has no permission fields (`frontend/src-tauri/src/onboarding.rs:205-218`). `handleSkip` sets `permissionsSkipped` (`steps/PermissionsStep.tsx:105-108`), which lives only in React state (`contexts/OnboardingContext.tsx:107`), is exposed on the context (`:626`) and has no consumer in the repository — and is destroyed by the `window.location.reload()` two lines later.

**Impact:** the recovery scenario produces no UI change at all. A user who clicks Enable, denies, opens System Settings, flips the toggle and tabs back to Minutes sees the same row in the same state, with Finish Setup still disabled, and nothing on screen telling them to click again — which after FR-04 means clicking a button that opens an alert. A quit at step 4 returns to step 4 with both rows back at `not_determined` regardless of what macOS already recorded. And afterwards, a user who took "I'll do this later" is indistinguishable from one who granted everything, so nothing can pre-empt the first recording failure. Structurally, the only step that needs a human is queued behind the longest unattended wait, and its result is the one thing the flow does not write down.

**Fix contract:** the step reads real permission state on mount and again whenever the window regains focus, from a backend query that reports state *without* triggering a prompt, and re-renders both rows and the Finish gate from that read; the click handlers remain the only prompting path. A "Check again" control stays visible in every non-authorized state. The outcome — granted, denied or deferred, per permission — is persisted alongside model status in `OnboardingStatus`, so the next boot knows what happened and can show a dismissible prompt on the recording surface for the deferred case; the step's copy then names a destination that exists. Let the permission conversation overlap the transfer rather than queue behind it, so the wait is spent on the part that needs a person. If persistence is not wanted, delete `permissionsSkipped` rather than leaving state that is written, read by nobody, and discarded by a reload.

### FR-08 · P2 — There is no permission recovery anywhere outside onboarding, and onboarding cannot be re-entered

**Evidence:** the boot gate renders the flow only when the stored status says incomplete (`app/layout.tsx:248-250, 271-277`), and `complete_onboarding` writes `completed = true` permanently (`frontend/src-tauri/src/onboarding.rs:210-218`). `reset_onboarding_status_cmd` exists and is registered (`onboarding.rs:161-168`, `lib.rs:1025`) but a repo-wide search finds **zero frontend callers** — nothing in settings, no debug menu, no palette entry. No file under `components/settings/` or `app/settings/` mentions permissions at all. Two components that would have been the recovery surface are orphaned: `components/PermissionWarning.tsx` and `hooks/usePermissionCheck.ts` are each imported by nothing. The one live failure surface is the generic recording-start error: `contexts/RecordingControllerContext.tsx:501-512` reports the raw backend string with `settingsSection: 'recording'`, and `components/RecordingControllerFeedback.tsx:23-31` renders an **"Open settings"** link into Minutes' own settings page — not macOS System Settings.

**Impact:** a user who grants both permissions, finishes setup, then revokes microphone access in System Settings has no route back. Recording fails with the backend sentence from `audio/devices/discovery.rs:158-161`, and the only offered action opens an in-app settings page containing nothing about permissions. Re-running setup requires deleting `onboarding-status.json` from the app's store directory by hand.

**Fix contract:** permissions get a durable home outside onboarding — a Permissions section in settings showing live state per permission, a per-permission button that opens the correct macOS pane, and a re-check control — and the recording-start permission failure links there instead of at `settingsSection: 'recording'`. Either adopt the already-written `PermissionWarning` / `usePermissionCheck` pair as that surface, after correcting `usePermissionCheck` to read permission state rather than device availability, or delete both; do not leave two unreachable implementations beside a gap. Expose the existing reset command behind a "Run setup again" action so onboarding is re-enterable.

### FR-09 · P2 — Setup ends on a disabled button and lands on a library that knows nothing about what just happened

**Evidence:** the last screen on macOS is titled "Grant Permissions" (`steps/PermissionsStep.tsx:115-117`), its primary button is `disabled={!allPermissionsGranted}` (`:149-151`), and the only other exit is an unstyled `<button>` in `text-neutral-500` reading "I'll do this later" (`:153-158`). ### FR-10 · P2 — `complete_onboarding` records both models as downloaded regardless of what is on disk

**Evidence:** `frontend/src-tauri/src/onboarding.rs:210-214` sets, unconditionally:

```rust

status.current_step = 4;
status.model_status.parakeet = "downloaded".to_string();
status.model_status.summary = "downloaded".to_string();
```

The command receives only a `model` string and never checks disk. It is reachable while the summary model is mid-download — `completeOnboarding` explicitly handles that case by firing a *new* download and continuing (`contexts/OnboardingContext.tsx:488-500`) — and `handleSkip` reaches it with no gate at all (`steps/PermissionsStep.tsx:105-108`). **Impact:** the persisted record of what setup achieved is fiction, and on the common path it is false the moment it is written, because the ~2.6 GiB summary model is still in flight. **Fix contract:** `complete_onboarding` derives `model_status` from the same discovery the engines already expose rather than asserting it, and persists a distinct state for "completed with downloads still in flight" so the next launch re-verifies instead of trusting a flag. ### FR-23 · P3 — Download-layer cleanup: a duplicated retry path, and no end-to-end size assertion on the summary download

**Evidence:** `contexts/OnboardingContext.tsx:574-582` defines `retryParakeetDownload` and exposes it on the context (`:66, 638`), but `DownloadProgressStep` does not call it — it has its own `handleRetryDownload` duplicating the same `invoke('parakeet_retry_download', …)` with separate state handling (`steps/DownloadProgressStep.tsx:64-104`). ## What I dropped, and where the probes disagreed

Every finding above was re-verified by opening the cited file. The following probe claims did not survive that pass, or did not belong in the findings list:

1. **"A Windows or Linux user can boot into a blank onboarding surface with no way out"** (proof probe, E5-09). The missing fallback renderer is real and is kept as FR-22, but I could find no reachable path to a saved `current_step: 4` with `completed: false` on a non-macOS profile — see FR-22's evidence. The dead-end impact claim is dropped; only the blank-frame and missing-fallback claims are kept.
2. **"A repo-wide grep for `Meetily` under `frontend/src` returns zero matches"** (messaging probe, finding 4). The capitalised string is indeed absent from user-facing copy, but lowercase `meetily` appears in nine places as storage keys, custom event names, a meeting-detection pattern and a legacy database path (`lib/liveNotes.ts:17-18`, `contexts/ShellContext.tsx:14`, `contexts/OnboardingContext.tsx:180`, and others). The underlying point — that `CLAUDE.md` calls the product Meetily while the shipped app says Minutes — is a documentation item with no first-run impact, so it is not a finding here.
3. **The Parakeet downloader's correct `finish_download` discipline** (network probe, finding 2) was filed as a finding. It is not a defect; it is the evidence that FR-06 is an asymmetry rather than an architectural limit, and it appears there instead.
4. **Resumability and bounded failure** (network probe, findings 5 and 6) are not defects either. They refute two reasonable concerns and are recorded in the Summary.
5. **Arithmetic corrected.** The walkthrough probe gave the summary model as 2,741,075,968 bytes and the clean-install total as 3,411,695,674 bytes. 2614 MiB is 2,740,977,664 bytes and the total is 3,411,597,370 bytes. The derived bandwidth figures are unaffected at the stated precision.
6. **Citation corrections.** The proof probe cited `SetupOverviewStep.tsx:116` for that step's number; it is `:50`. The messaging probe cited `DownloadProgressStep.tsx:45` for the "670 MB" label; `:45` is the initial `totalMb: 670` state field and `:505` is the rendered string. The walkthrough probe described the indicator dots as 24–28 px; the classes are `w-6`/`w-7`/`w-8`, so 24–32 px.
7. **Contradiction resolved on the summary model's size.** The messaging probe described it as a "~1.0–2.6 GiB" range; the walkthrough probe said always ~2.6 GiB. The walkthrough probe is right for a clean install: `recommend_summary_model` ignores both its arguments and returns `qwen3.5:4b` unconditionally (`summary/summary_engine/commands.rs:21-23`), so the smaller catalogue entries are reachable only through a previously saved `selected_summary_model`.
8. **Scoped, not dropped.** The permissions probe described `verify_microphone_access` as "wired into the record-start path" without qualification. It is — but only on macOS, because its sole caller is cfg-gated (`recording_commands.rs:525, 637-638, 866-867`). That qualification is what FR-16 is about.
